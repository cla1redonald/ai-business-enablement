# The engagement workspace

Every engagement runs in its own workspace folder outside this repo. Live client
workspaces never enter the repo. The only exception is the synthetic workspace under
`fixtures/`, which is the worked example. The four tools work on this layout and on
nothing else.

```
<engagement>/
  engagement.json        the engagement config (see below)
  intake/
    registry.md          name-to-token mapping. NEVER leaves the workspace;
                         never cited, never packed
    sources.md           the source ledger: one row per source: file, sub-type,
                         conversation/document, status (accepted/refused + why),
                         and label adequacy (do the labels separate the client
                         speakers, or is attribution content-only?)
  sources/               the inputs as received (raw names allowed here only)
  observations/          one JSON file per accepted source (obs-<source_id>.json)
  data/
    landscape.json       confirmed opportunities, streams, gaps (post-gate)
    readiness.json       confirmed 20-area ratings and findings (post-gate)
  facts.json             generated by tools/facts.py; never edited
  artefacts/
    report.md            human-written on the skeleton
    summaries/           tokenised call summaries (pack-facing)
    maps/                generated value-stream maps
    briefs/              generated enabling-gap briefs
    workbook.xlsx        generated by tools/workbook.py
  packs/
    <Client>_V<n>/       immutable baselines from tools/pack.py (plus .zip)
```

## engagement.json

```json
{
  "schema_version": "0.1",
  "client_display": "Caldergate Freight",
  "consultancy": "{the skin's firm name, or the consultant's}",
  "consultant_role_token": "[CONSULTANT-1]",
  "period": "September to October 2027",
  "evidence_period": "September 2027",
  "names": ["surnames and forenames for the checker ban list"],
  "company_tokens": {"[CLIENT-A]": "prospect/customer orgs, token to nothing"}
}
```

The client's own name appears in its deliverables, but **other** organisations
(prospects, customers, and suppliers where that is sensitive) are tokenised. The
`names` list feeds the engagement's copy of `check.config.json`. Artefacts may contain
the `company_tokens` keys, and the values they map to exist only in this file.

## data/landscape.json (confirmed at the gate)

```json
{
  "schema_version": "0.1",
  "opportunities": [{
    "id": "OPP-001", "name": "...", "description": "...",
    "functions": ["Sales"], "streams": ["VS-01"],
    "impact": "High", "effort": "Low",
    "quantified": {"figure": 2.5, "unit": "hours per week"},
    "gaps": ["GAP-01"], "sources": ["<source file name>"]
  }],
  "streams": [{
    "id": "VS-01", "name": "Quote request to booked shipment",
    "statement": "...", "start": "...", "end": "...",
    "functions": ["Sales", "Operations"], "impact": "High",
    "sources": ["<source file names>"]
  }],
  "gaps": [{
    "id": "GAP-01", "name": "...", "enabler": "Trusted information",
    "status": "Gap", "wave": 1, "owner": "to be named"
  }]
}
```

The tools enforce these rules.

- IDs are stable and never reused.
- `impact`, `effort`, `functions` and `streams` may be null or empty. That is a gap in
  the data, which is counted and reported, and never an error.
- `quantified` is either present with a figure AND a unit, or absent entirely.
- An opportunity's `gaps` and `streams` must reference IDs that exist.
- Waiting counts for each gap, and membership and source counts for each stream, are
  always derived and never stored.

## data/readiness.json (confirmed at the gate)

```json
{
  "schema_version": "0.1",
  "areas": [{
    "n": 1, "area": "System connectivity", "enabler": "Trusted information",
    "rating": "partial", "observed_directly": false,
    "finding": "...", "action": "...", "sources": ["<source file name>"]
  }]
}
```

There are exactly 20 areas, four per enabler, in canonical order, and every rating
comes from the four-value scale. `facts.py` derives the roll-up counts.

## observations/obs-<source_id>.json

This is the working layer between a source and the landscape. It follows the shape of
`skills/schemas/landscape-observation.schema.json`, cut down to the minimum.

```json
{
  "source": "<source file name>", "sub_type": "discovery interview",
  "observations": [{
    "id": "OB-001", "claim": "...",
    "quote": "verbatim from the source", "locator": "<file>, S2",
    "confidence": "medium",
    "scale": {"cadence": "...", "load": "...", "held_by": "..."},
    "stated_dependencies": "the speaker's own linkage, as a quote",
    "relay": true
  }]
}
```

The `scale` keys and `stated_dependencies` appear only when the source states them.
`relay: true` marks the one exception for second-hand relays. In that case the quote
rightly sits in a consultant turn, the claim counts as indirect client evidence at
reduced confidence, and the checker warns rather than failing it. Any other quote
from a consultant turn fails.
