A shared verification pattern, so answers can be shown right before reliance

The usage note already requires competent review before anything is relied on; what is missing is any shared way of doing that check, so each build stands or falls on its own luck.

Enabler: Control and accountability · Status: Gap · Opportunities waiting: 5 · Owner: to be named · Wave: 1

Skills this needs

Skills are derivable from the work. Days are not, without knowing scope and who is doing it, so no estimate is given: putting a number against work nobody has been asked to do would imply a decision that has not been made.

This is not a hiring problem. The people who know what a correct answer looks like are already in the business (the customs clerk, the customer service lead, the sales desk), and the scripting capability exists in a 2-person IT function whose every hour is already committed. That is a scheduling decision, not a capability gap, and it is why protected learning time is itself one of these enabling gaps.

What is missing, and why

The interim usage note requires anything the assistant produces to be checked by someone competent before it is relied on. Nothing implements that requirement and nothing records that it happened.

The cost is already real. The customer service FAQ assistant answered the most-asked question well until it gave one customer a stale cut-off, confidently, and a shipment missed its sailing. Nothing could have shown the answer was wrong before it went out, and that, in the team's own reading, is what killed the tool rather than the mistake itself.

The people closest to the work name the requirement better than the note does. The customs clerk, offered a working demonstration of mechanical document checks, set the bar as right every time, because a wrong all-clear is worse than no check. The sales lead keeps AI away from rates entirely until it can read only the actual rate cards. Both are asking for the same thing: a way to show an answer is right before anyone leans on it.

What it releases

These opportunities cannot start, or cannot finish, until this enabling gap is closed.

  • Quote assembly assisted from the rate cards, scoped read-only high impact
  • Cut-off answers, verified and current high impact
  • Status queries answered from the systems high impact
  • Customs document pre-check at the booking desk high impact
  • Tender fill assistance medium impact

Routes

Options, not a recommendation. Each states what it assumes, because the assumption is usually the thing to test first.

Enforce the review clause at the point of publication

impact: higheffort: low

The usage note already requires competent review before reliance. Asking for evaluation evidence whenever a tool is shared through the new publish route makes the requirement bite at the one moment somebody is already looking.

What it assumes. Nothing assumed. This is enforcement of an existing rule, and it only works alongside the publish route (its own brief).

Build the first harness on the cut-off answers

impact: higheffort: low

The failed FAQ assistant is the best possible first case: the correct answers are knowable, the failure mode is known (staleness), and the team has said plainly it would use a verified version tomorrow. Twenty to fifty realistic cases with expected answers, agreed with the CS lead, run before anything reaches a customer.

What it assumes. That operations keeps the cut-off source current, which is a findability and ownership question as much as a tooling one. Test that assumption first; the harness will otherwise verify against a stale truth.

Build verification into the tools rather than the process

impact: higheffort: medium

A tool that carries its own checks is enforceable in a way a policy clause is not. It travels with the tool, runs every time, and does not depend on anyone remembering.

What it assumes. This is the durable answer, and the slowest. The two routes above buy time for it.
